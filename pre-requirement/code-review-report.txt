Prequel = AI 인터뷰 기반 프로젝트 기획 검증 웹툴

  Backend : FastAPI(Python) + Supabase + Alembic
            27개 파일 / 약 2,900 LOC (api / core / models / schemas / middleware)
  Frontend: React + TypeScript + Vite
            58개 파일 / 약 7,100 LOC (components / contexts / hooks / pages / i18n)
  합계    : 풀스택 모노레포 약 10,000 LOC

핵심 전제(보안 관점):
  백엔드가 Supabase SERVICE_KEY로 접속(core/supabase.py:11) → RLS 우회.
  따라서 모든 권한 검사는 애플리케이션 코드가 직접 책임져야 함.
  즉, 각 엔드포인트가 user_id로 쿼리를 스코핑하지 않으면 곧바로 IDOR 취약점이 됨.

[ Critical 1 — 권한 검사 누락 (IDOR / Broken Access Control) ]
================================================================================
근본 원인:
  POST(생성) 계열은 project_id + user_id로 소유권을 잘 검증하지만,
  session_id를 받는 조회/수정 엔드포인트는 "그 세션이 호출자 소유인지" 확인하지 않고
  바로 조회/수정함. SERVICE_KEY라 DB단에서도 안 막힘.

영향 엔드포인트:
  design.py:210   GET /requirements/{session_id}            → 타인 데이터 열람
  design.py:228   PUT /requirements/{session_id}/{req_id}   → 타인 데이터 수정
  design.py:266   PUT /requirements/{session_id}            → 타인 데이터 덮어쓰기
  design.py:443   GET /architecture/{session_id}            → 열람
  design.py:461   PUT /architecture/{session_id}            → 수정
  design.py:545   GET /data-model/{session_id}              → 열람
  design.py:563   PUT /data-model/{session_id}              → 수정
  finalize.py:248 PUT /{step}/{session_id}                  → 수정

공격 시나리오:
  로그인한 사용자 A가 session_id만 B의 세션 값으로 바꿔 호출 → B의 설계 내용을
  읽거나 덮어쓸 수 있음. UUID라 추측은 어렵지만 "인증 통과 = 인가 무방비" 상태.
  전형적 OWASP A01(Broken Access Control).

해결 방향:
  세션→프로젝트 조인으로 user_id를 확인하는 공유 헬퍼
  (_verify_session_owner(session_id, user_id))를 만들어 8개 모두에 적용.
  finalize.py엔 이미 _verify_project가 있으나 update_finalize_step에는 안 걸려 있음.

[ Critical 2 — 크레딧 증가 경쟁 조건 (과금/한도 우회) ]
================================================================================
위치: projects.py:34-38  _increment_credits()

문제:
  credits_used를 읽고 +1을 쓰는 비원자적(read-modify-write) 연산.
  무료 사용자가 generate 요청을 병렬로 N개 쏘면 전부 used=0을 읽고 통과 →
  무료 한도(2회)를 우회해 N회 생성 가능. 수익화 단계에서 매출 누수/한도 무력화 직결.

해결 방향:
  DB 원자적 증가로 변경.
  예) Postgres RPC 또는 update ... set credits_used = credits_used + 1

[ High 3 — 할당량 표시 영구 오작동 (free_used ↔ credits_used) ]
================================================================================
원인:
  백엔드 schemas/user.py는 credits_used를 반환하는데, 프론트는 free_used를 읽음.
  API가 free_used를 절대 안 보내므로 항상 undefined → 0.

영향 위치:
  useAuth.ts:12        free_used: number   (타입 정의 — 백엔드와 이름 불일치)
  MyProjectsPage.tsx:66 user?.free_used ?? 0  → 항상 0
  TopBar.tsx:35        user?.free_used ?? 0  → 항상 0

실제 영향:
  - 헤더 "잔여 2/2", 대시보드 "이번 달 사용 0/2"가 실사용량과 무관하게 고정
    (TopBar.tsx:97, MyProjectsPage.tsx:119)
  - MyProjectsPage.tsx:88 isQuotaExceeded = ... freeUsed >= 2 → 항상 false
    → "새 프로젝트" 버튼이 클라이언트단에서 절대 안 막힘
      (서버 _check_credits는 막지만, UX·클라 가드가 죽음)

해결 방향:
  useAuth.ts의 UserProfile 타입을 credits_used로 통일하면 3곳 동시 해결.
  부가: useAuth.ts UserProfile엔 suspended_at/deleted_at 누락 등 백엔드 스키마와
        타입 드리프트 존재 → 공유 타입 한 곳으로 정리 권장.

[ High 4 — 데이터 모델 수동 편집이 저장 안 됨 (데이터 손실) ]
================================================================================
설계 단계에서 RequirementsStep과 DataModelStep의 저장 처리가 불일치.

  RequirementsStep.tsx:36-48 : persist() → PUT /design/requirements/{id} 호출 (정상)
  DataModelStep.tsx:41-94    : onUpdateSession(setSession)만 호출, PUT 없음 (버그)

상세:
  DataModelStep의 removeEntity / addEntity / addFieldToEntity / removeRelationship
  4개 모두 로컬 React state만 갱신하고 백엔드에 안 보냄.
  백엔드 PUT /design/data-model/{session_id}(design.py:563)는 존재하는데
  프론트가 호출하지 않음 → 배선 누락.

체감 시나리오:
  사용자가 엔티티·필드를 추가/삭제 → 푸터엔 "자동 저장됨" 표시 →
  새로고침하면 AI 생성 원본으로 롤백. 편집 기능이 사실상 무력.

해결 방향:
  RequirementsStep의 persist 패턴을 그대로 복제해 PUT 호출 추가.
