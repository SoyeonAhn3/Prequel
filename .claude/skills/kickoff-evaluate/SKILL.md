# kickoff-evaluate Skill

킥오프 + 설계 문서가 완성된 후, "이 프로젝트가 정말 목적에 맞는가?"를 4+2개 차원으로 솔직하게 평가하는 스킬. gap이 "문서 내 모순/누락"을 잡는다면, evaluate는 "프로젝트 자체의 가치와 실현가능성"을 판단한다.

핵심 프레임: **"설계까지 마친 후 평가해야 정확한 판단이 가능하다."**

---

## 사전 조건

- 킥오프 문서(`{프로젝트명}_kickoff.md`)가 존재해야 함
- 대화 컨텍스트에 경로가 없으면 Glob으로 `**/*_kickoff.md`를 검색
  - 0개 발견: `/kickoff-start`를 먼저 실행하도록 안내
  - 1개 발견: 해당 파일 Read → YAML frontmatter 확인
  - 2개 이상 발견: frontmatter에 `completed_skills` 필드가 있는 파일만 대상, 여러 개면 사용자에게 선택 요청
- YAML frontmatter `completed_skills`에 `design-data-model`이 포함되어야 함
  - 추가로 `design-ai-workflow`가 `completed_skills` 또는 `skipped_skills`에 포함되어야 함
  - 조건 미충족 시: 설계 스킬(`/design-requirements` → `/design-architecture` → `/design-data-model` → `/design-ai-workflow`)을 먼저 실행하도록 안내
- **변경 감지**: YAML frontmatter `section_versions`를 확인하여, 의존 섹션(1, 2, 3, 4, 9, 10, 11, 12)이 현재 섹션(7) 작성일 이후에 수정되었는지 점검. 변경 감지 시 사용자에게 영향 알림 후 재생성/유지 선택을 받는다. 최초 실행(섹션 7 미작성) 시 건너뜀.
- 킥오프 문서 `### 프로젝트 배경` 서브섹션이 있으면 목적 기반 평가 활성화, 없으면 일반적 평가만 수행

## STEP 1 — 입력 수집

킥오프 문서를 읽어 평가에 필요한 정보를 수집한다.

### 수집 대상

| 출처 | 수집 항목 |
|---|---|
| 킥오프 문서 `### 프로젝트 배경` | 프로젝트 목적, 기술 수준, 시간 예산, 차별화 방향 |
| 킥오프 문서 섹션 1 | 유형, 핵심 기능, 기술 스택, 제약사항 |
| 킥오프 문서 섹션 2~4 | 아키텍처, 데이터 구조, 실패 시나리오 (있는 경우) |
| 킥오프 문서 섹션 9 | 요구사항 정의 (FR, NFR, 사용자 흐름) |
| 킥오프 문서 섹션 10 | 시스템 아키텍처 |
| 킥오프 문서 섹션 11 | 데이터 모델 |
| 킥오프 문서 섹션 12 | AI 워크플로우 (AI 프로젝트인 경우) |

### 조건부 차원 활성화 판단

수집된 정보로 조건부 차원 활성 여부를 결정한다:

| 조건부 차원 | 활성화 조건 | 판단 기준 |
|---|---|---|
| 학습 비용 | 목적이 포트폴리오 또는 학습 | `### 프로젝트 배경`의 프로젝트 목적 |
| 보안 적절성 | 웹/앱 프로젝트 + 외부 사용자 존재 | 유형 + 사용자 정보 |

- context 없으면 조건부 차원 비활성 (항상 적용 4개만 평가)

## STEP 2 — 차원별 평가 수행

`references/evaluation-criteria.md`를 참조하여 활성화된 차원별로 평가한다.

### 평가 차원 (4+2 구조)

**항상 적용 (4개)**:

| # | 차원 | 핵심 질문 |
|---|---|---|
| 1 | 차별화 | 이 프로젝트가 목적에 맞게 눈에 띄는가? |
| 2 | AI 적절성 | AI라 부르기 적절한가? 규칙 기반으로 대체 가능한가? |
| 3 | 시장 유효성 | 6개월 뒤에도 유효한가? 유사 프로젝트가 범람하지 않는가? |
| 4 | 완성도 기대치 | 실제 동작하는 데모가 나올 수 있는가? |

**조건부 적용 (2개)**:

| # | 차원 | 핵심 질문 | 활성화 조건 |
|---|---|---|---|
| 5 | 학습 비용 | 수준 대비 배울 게 과다하지 않은가? | 포트폴리오 또는 학습 목적 시 |
| 6 | 보안 적절성 | 인증/인가, 민감 데이터 처리가 고려되었는가? | 웹/앱 + 외부 사용자 시 |

### AI 적절성 차원 적용 규칙

- 아래 **두 조건 중 하나라도** 해당하면 상세 평가:
  1. 프로젝트 유형에 "AI"가 포함된 경우
  2. 기술 스택에 AI API/모델이 포함된 경우 (예: Claude API, GPT API, Gemini API, HuggingFace, TensorFlow, PyTorch 등)
- 두 조건 모두 해당하지 않는 경우: "해당 없음"으로 표시하고 건너뜀
- 유형은 "AI"가 아니지만 기술 스택에 AI가 포함된 경우: "AI를 핵심 기능으로 사용하는 [유형] 프로젝트"로 인식하고, AI 의존도와 대체 가능성을 중점 평가

### 판정 체계

| 판정 | 의미 | 후속 조치 |
|---|---|---|
| 🟢 적합 | 문제 없음 | 없음 |
| 🟡 조건부 | 개선하면 더 좋음 | 구체적 개선 제안 제시 |
| 🔴 재검토 | 방향 자체에 문제 | 대안 제시 + 사용자 결정 요청 |

## STEP 4 — (선택) 범위 조정 반영

사용자 선택에 따라 처리한다.

### 사용자 반응별 처리

| 선택 | 처리 |
|---|---|
| 1. 유지 | 평가 결과만 기록, STEP 5로 이동 |
| 2. 조정 | 사용자와 조정 논의 → 킥오프 문서 해당 섹션 Edit으로 수정 → **영향 차원 재평가** → 수정 내용 요약 기록 |
| 3. 전환 | 방향 전환 논의 → 필요 시 `/kickoff-interview`부터 재실행 안내 |

### 조정 후 문서 연쇄 갱신 (2번 선택 시)

MVP 범위가 변경되면, **영향 차원 재평가 전에** 킥오프 문서의 관련 필드를 순회하여 불일치를 수정한다.

#### 연쇄 갱신 체크리스트

기능이 MVP ↔ v2로 이동할 때, 아래 6개 필드를 순서대로 점검한다:

| # | 체크 필드 | 점검 규칙 | 수정 방법 |
|---|---|---|---|
| 1 | 핵심 기능 행 분리 | 이동된 기능이 다른 기능과 한 행에 묶여있는지 | 필수/선택을 별도 행으로 분리, MVP 포함 컬럼 갱신 |
| 2 | 기본 정보 → 결과 형태 | 결과 형태가 v2 기능을 포함하는지 | MVP/v2 분리 표기 (예: "MVP: X / v2: Y") |
| 3 | KPI 후보 | v2로 이동된 기능의 KPI가 남아있는지 | "(v2)" 또는 "(범위 외)" 표기 추가 |
| 4 | 기술 스택 | v2 전용 기술이 필수로 남아있는지 | "(v2)" 표기 추가, 선택 이유에 "(v2 시 필요)" 명시 |
| 5 | 외부 서비스 의존성 | v2 기능에만 필요한 서비스가 "필수"인지 | 필수 → 선택으로 재분류, "(v2)" 표기 |
| 6 | 실패 시나리오 | v2 전용 시나리오가 포함되어있는지 | "(v2)" 표기 추가 또는 비고란에 범위 명시 |

#### 수행 순서

1. 이동된 기능 목록 확인 (어떤 기능이 MVP → v2 또는 v2 → MVP로 이동했는지)
2. 6개 필드를 순서대로 점검
3. 불일치 발견 시 수정안을 사용자에게 제시
4. 사용자 확인 후 Edit으로 수정 + `(평가 후 조정됨)` 표기
5. 모든 연쇄 갱신 완료 후 영향 차원 재평가로 진행

#### 점검 범위 판단

- 이동된 기능과 **직접 관련된 필드만** 점검 (전체 문서 재검토가 아님)
- 이미 올바르게 분리/표기된 필드는 건너뜀
- 설계 인터뷰를 패스한 경우 (섹션 2~4 없음): 필드 6은 해당 섹션이 없으면 건너뜀

### 조정 후 영향 차원 재평가 (2번 선택 시)

MVP 범위가 변경되면, 영향받는 차원에 대해 STEP 2를 다시 수행한다:

| 조정 유형 | 재평가 대상 차원 |
|---|---|
| 핵심 기능이 v2로 이동 | 차별화, 완성도 기대치 |
| AI 기능이 v2로 이동 | 차별화, AI 적절성 |
| 기술 스택 변경 | 완성도 기대치, 학습 비용(활성 시) |
| 사용자/범위 변경 | 차별화, 시장 유효성 |

**유형 재판별 트리거**: AI 관련 기능이 전부 v2로 밀렸을 때, 킥오프 문서 Section 1 `### 기본 정보`의 부가 유형에서 "AI 프로젝트"를 제거할지 사용자에게 확인한다. 유형이 변경되면 AI 적절성 차원을 "해당 없음"으로 전환한다.

### 유형 변경 시 킥오프 문서 갱신

사용자가 유형 변경을 확인하면, 킥오프 문서를 Edit으로 갱신한다:

1. **`### 기본 정보` 테이블의 "유형" 행**: 변경된 유형으로 교체 + `(평가 후 조정됨)` 표기
2. **변경 전후 안내**: 사용자에게 변경 내용을 명시적으로 보여줌

```
유형이 변경되었습니다:
- 변경 전: [주 유형] + [부가 유형]
- 변경 후: [주 유형] (부가 유형 제거)

킥오프 문서 `### 기본 정보`가 갱신되었습니다.
```

3. **연쇄 영향 확인**: 유형 변경으로 인해 아래 항목도 재확인이 필요할 수 있음을 안내
   - 섹션 5(gap 점검)에서 유형 기반으로 점검한 항목
   - 섹션 6(체크리스트)에서 유형 기반으로 생성한 항목

재평가 결과가 기존 판정과 다를 경우, 변경된 판정으로 갱신하고 사용자에게 변경 사항을 안내한다.

### 조정 시 주의사항

- 킥오프 문서 수정 시 기존 섹션 구조를 유지
- 수정된 부분에 `(평가 후 조정됨)` 표기
- 설계 섹션(9~12)과 충돌하는 수정이 없는지 확인

## STEP 5 — 파일 업데이트 및 상태 저장

```markdown
| 3 | 시장 유효성 | [판정] | [피드백] |
```

### YAML frontmatter 갱신

킥오프 문서의 YAML frontmatter `last_skill`을 `kickoff-evaluate`로 변경, `completed_skills`에 `kickoff-evaluate` 추가, `section_versions`의 섹션 7 키를 오늘 날짜(`YYYY-MM-DD`)로 갱신 (Edit 사용)

### 안내 출력

```

`{프로젝트명}_kickoff.md` 섹션 7이 업데이트되었습니다.
```

이 스킬은 **킥오프 문서를 직접 업데이트**한다:
- 대상: `{프로젝트명}_kickoff.md` 섹션 7
- 방식: 섹션 7 플레이스홀더를 평가 결과로 교체 (Edit 사용)
- YAML frontmatter `last_skill` 및 `completed_skills` 갱신

---

## 실패 처리

| 실패 유형 | 처리 방법 |
|---|---|
| 킥오프 문서 없음 | `/kickoff-start`를 먼저 실행하도록 안내 |
| 설계 스킬 미완료 | 설계 스킬 체인(`/design-requirements` → ... → `/design-ai-workflow`)을 먼저 실행하도록 안내 |
| 섹션 7 플레이스홀더 없음 | 파일 하단에 섹션 7을 새로 추가 |
| context 없음 | 조건부 차원 비활성, 항상 적용 4개만 평가 + "context 없이 일반 평가만 수행됨" 안내 |
| 사용자가 결과에 강하게 반발 | "이 평가는 참고용이며, 최종 결정은 사용자에게 있습니다" 안내 후 유지로 기록 |
| AI 유형이 아닌데 AI 적절성 질문 | "해당 없음"으로 건너뜀 |

---

## 주의사항

- 🔴도 **"그만둬라"가 아니라 "이렇게 바꾸면 된다"** — 대안 없는 🔴 판정 금지
- 평가가 사용자를 **낙담시키면 안 됨** — 건설적 피드백 프레임 유지
- context 없이 실행해도 동작 (일반적 평가만, 목적 특화 불가)
- 보안/학습 비용 차원은 조건부 — 해당하지 않는 프로젝트에 강요하지 않음
- 반드시 킥오프 문서를 **Read 먼저** → 이후 Edit으로 추가
- 이미 섹션 7에 내용이 있으면 (재실행 시) 기존 내용을 교체
